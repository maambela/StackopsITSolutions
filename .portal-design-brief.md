# Client portal feature-story brief

## Objective
Add a premium "Why Choose Our Client Portal?" feature section to the existing `Home.html` marketing page. The desktop experience must recreate the scroll relationship from the supplied recording: as the visitor scrolls, only the left feature narrative advances while a large visual stays pinned on the right; once all four stories have passed, the section releases and the two columns move with the page together.

## Audience and direction
Target South African business decision-makers evaluating managed IT. Match the existing StackOps dark, technical, high-end visual language, but make the new area more editorial and assured than a generic card grid. Use the existing site typography and palette (ink/black background, electric blue/cyan, cool white). The memorable element is a large, realistic portal/dashboard visual that stays framed like a live command center while the copy sequence scrolls beside it.

## Required content
- Kicker: `Client portal`
- H2: `Why Choose Our Client Portal?`
- Intro: `Enterprise-grade features designed for your success`
- Four items, in this order, each with a small sequence number and the supplied title/body exactly:
  1. `Unified Command Center` — `Consolidate your entire IT footprint—from Microsoft 365 to Backup & Recovery—into one simplified, high-performance portal.`
  2. `Zero-Trust Peace of Mind` — `Live identity monitoring and encrypted governance ensure your business data is shielded by enterprise-grade protocols 24/7.`
  3. `Executive Decision Intelligence` — `Stop guessing. Our dashboard provides actionable, real-time insights that allow you to make data-driven decisions in seconds.`
  4. `Mobile Responsive` — `Access your dashboard from any device - desktop, tablet, or mobile phone.`

## Interaction and responsive behavior
- On desktop/tablet landscape (min-width about 900px): two columns, text left and a large visual right. Use `position: sticky` with a sensible viewport top offset on the visual-side inner wrapper, so only the left content scrolls during the feature list. Do not use scroll-jacking, JS-driven scroll transforms, or an animation library. The parent must be tall enough for all items; the sticky element releases naturally at its bottom so both columns then scroll together.
- Give each feature enough vertical breathing room to create the desired progression. Add an accessible, reduced-motion-safe active state (IntersectionObserver is acceptable) that makes the currently read item more prominent and updates a small progress rail / screen annotation. The content must remain fully readable with JavaScript disabled.
- On phones and narrow tablets: turn off sticky behavior entirely. Place the visual near the top after the title/intro, then show each feature in a normal vertical list; no horizontal overflow, clipped text, or tiny type. Design explicitly for 320px wide phones.

## Image needs
Use existing local project assets for the primary portal visual where possible—prefer `Images/Screenshot1.png`, `Images/Clientdashboard.png`, or other suitable existing dashboard/interface imagery. Do not link to Unsplash/Pexels/external image services. If supplementary imagery is needed, use local assets only. The image needs to be easy for the user to replace later: keep it as a clearly named `<img>` with a conventional local `src` and descriptive `alt`, not as a CSS background.

## Placement and implementation
- Integrate into the real application page: edit `Home.html` and `latest.css`, and only add small inline JavaScript in `Home.html` if needed for the active sequence.
- Place the new section after the existing featured solutions section and before the services grid, unless surrounding markup indicates a more natural equivalent location.
- Namespace all new selectors under `portal-story` to avoid existing CSS collisions. Append override CSS at the end of `latest.css` rather than restructuring unrelated style blocks.
- Preserve all unrelated work. Avoid external dependencies. Ensure valid semantic markup and headings.

## Verification
Run a syntax/brace-balance check and use the available browser tooling or existing local server to inspect desktop and narrow mobile layouts before reporting completion.
